# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Qué es

Vita-Web ("vita.ia") es una app de salud personal — medicamentos, turnos médicos, perfil de salud, y un asistente de chat con IA ("vita") que puede leer y modificar esos datos. Nació como la reconstrucción del *dominio* de [`ijproyectos/Vitapp`](https://github.com/ijproyectos/Vitapp) (Flutter + Go + Python, en etapa temprana) sobre la arquitectura de NutrIA (Next.js + Supabase + Anthropic API), pero la UI/UX real terminó viniendo de un tercer diseño propio del usuario — ver "Identidad visual y funcionalidad" abajo, es la fuente de verdad actual, no el Flutter original.

A diferencia de NutrIA (multi-tenant, profesional↔paciente), Vita-Web es **single-tenant por usuario** — cada persona ve y gestiona solo sus propios datos, sin ningún rol ni jerarquía.

## Project state (2026-09-14)

**Reconstrucción completa sobre el diseño "vita.ia"** (`pantallas/Vitaoriginal/vita (1)/`, un export JSX real con toda la lógica de navegación en `vita.ia.html`) — reemplazó dos iteraciones de diseño anteriores en esta misma sesión (el Flutter original y un bundle brutalista intermedio, ninguno de los dos vigente). `apps/web/` es Next.js 16 (Turbopack, App Router) — build y lint limpios.

**Principio de alcance seguido**: `vita.ia.html` (el harness del diseño) es explícito sobre qué interacciones son reales (navegan a una pantalla) y cuáles son placeholders (`showToast('...próximamente')`, o ni tienen `onClick`) — se replicó esa misma frontera, no se fabricó funcionalidad real donde el propio diseño no la definió (Gmail/Apple Health/Google Fit, notificaciones push, monitoreo de métricas de salud, micrófono — exportar datos y eliminar cuenta se construyeron después a pedido explícito del usuario). Única desviación deliberada: "Cerrar sesión" se hizo real (el archivo original no lo cablea a nada, es un descuido del mock, no una decisión de producto — toda app real necesita poder cerrar sesión).

API estable: `VitaAvatar({ size, estado, interactivo?, activo? })`; `interactivo` default `size >= 56`; los chicos (burbujas, onboarding) se renderizan a ~10 fps y sin interacción.

Interacciones: mirada al puntero con resorte (k=60, c=12), mirada autónoma tras 2.5 s quieto, hover agranda ojos, toque = aplaste+parpadeo+saludo, saltito de entrada, parpadeo; 4+ toques en 2 s → enojo ~3 s. `prefers-reduced-motion`: solo respiración y parpadeo.

Se eligió Groq y no OpenAI directo porque OpenAI pide créditos pagos desde el primer request y Groq tiene free tier sin tarjeta. El transcript entra por el mismo `enviar()` de siempre (no hay un segundo path de envío). La respuesta de vita **ya no se lee con la voz de sistema del navegador** (`window.speechSynthesis` sonaba robótica, sin pausas — pedido explícito del usuario) — ahora se sintetiza server-side con **Deepgram Aura-2** (`POST /api/voz/hablar`, voz `aura-2-antonia-es`: femenina, acento argentino — confirmado contra `GET /v1/models` de Deepgram, no contra la doc genérica, es la única de las 17 voces en español del catálogo con `accent: "Argentine"`; se probó primero `sirio-es` pensando que era neutra y resultó ser acento mexicano) y se reproduce como mp3 con `<audio>` (`lib/voz/hablar-cliente.ts`). Antes de sintetizar se sacan los emojis del texto (`quitarEmojis` en `lib/voz/nucleo.ts`) — el TTS los pronunciaba como palabras ("emoji de mano saludando"); no se tocan en la burbuja del chat, solo en lo que se manda a Deepgram. Se descartó Groq para esto porque su TTS (Orpheus) es solo inglés/árabe, sin español. El desbloqueo de audio para Safari/iOS (llamada sincrónica dentro del click, antes de cualquier `await`) sigue siendo necesario y ahora desbloquea un `<audio>` en vez de `speechSynthesis` — son dos flags de permiso independientes en WebKit. **Habla por oración, no espera la respuesta entera**: `enviar()` acumula el texto en streaming y llama a `extraerFrasesListas()` en cada chunk (`lib/voz/hablar-cliente.ts`) — apenas se completa una oración (termina en `. ! ? …`) se encola para sintetizar (el fetch a Deepgram arranca ya, en paralelo a lo que se esté reproduciendo) y reproducir en orden; lo que queda sin punto final al cerrar el stream se habla igual al final. Antes esperaba el texto completo y recién ahí generaba un solo bloque de audio — se sentía "trabada" (silencio largo, después un chorro entero) — pedido explícito del usuario de que "conteste antes" y suene más fluida. Degrada explícito, nunca rompe el chat: sin `GROQ_API_KEY`/`DEEPGRAM_API_KEY`, sin micrófono, o si el navegador no soporta `MediaRecorder`/`getUserMedia`, avisa por toast (o simplemente no reproduce audio) y el usuario sigue viendo la respuesta en texto normal.

## Notas para código futuro en este repo

- **Núcleo de dominio separado de la UI y del chat**: `lib/medicamentos/nucleo.ts`, `lib/turnos/nucleo.ts`, `lib/perfil/nucleo.ts` — funciones puras `(supabase, usuarioId, ...) => resultado`, consumidas tanto por Server Actions como por tools de chat en `lib/ai/tools.ts`. No implementar la misma operación dos veces.
- **`lib/rutina/momento.ts`** — `momentoDelDia(hora)` deriva mañana/mediodía/tarde/noche desde una hora "HH:MM"; usado tanto por medicamentos (el form nuevo no pide momento_dia directo, lo infiere) como por turnos (que no tienen columna propia, se agrupan en la Rutina con este mismo criterio).
- **`useChatOverlay()`** (`lib/chat/overlay-context.tsx`) — para abrir el chat con vita desde cualquier pantalla (`abrir(mensajeOpcionalDeVita)`). El mensaje opcional se agrega como si vita lo preguntara, nunca se auto-envía nada en nombre del usuario (evita una llamada a la API sin que el usuario haya tocado nada).
- **Server Actions nunca lanzan** — devuelven `{status: "success"|"error", ...}` (`EstadoAccion` en `rutina/actions.ts`). Cualquier campo dentro de un `<form action={fn}>` tiene que ser controlado, no `defaultValue`.
- **`setState` síncrono en el cuerpo de un `useEffect` dispara `react-hooks/set-state-in-effect`** — patrón usado para resolverlo en este repo: si el estado solo necesita "no volver a pedir esto", usar un `useRef` en vez de `useState` (no es reactivo, no cae en la regla); si el estado SÍ es visible en el render (ej. "escribiendo…"), inicializarlo con el valor correcto en el `useState` inicial y mover cualquier "reactivación" al event handler que dispara el cambio (nunca al cuerpo del efecto) — ver `_chat/vita-chat-overlay.tsx` y `onboarding/chat/encuesta.tsx` para los dos casos reales.
- **Asignar a un ref durante el render** (`ref.current = x` fuera de un handler/efecto) dispara `react-hooks/refs` — solo asignar refs dentro de event handlers o efectos.
- **`Date.now()`/`Math.random()` en el cuerpo de un Server Component** disparan el lint de pureza — usar `new Date()` en su lugar (sí lo tolera).
- **`<Button render={...}>` con algo que no sea un `<button>` real** (ej. `<Link>`) necesita `nativeButton={false}` explícito.
- **Un `<option>` "Otra" con texto libre nunca debe usar ese mismo texto como `value`** — si el dato viejo (de antes de existir el picker) resultara ser literalmente igual al label de esa opción, el form la interpreta como "elegiste Otra, especificá" y vacía el campo de texto libre, borrando el dato al guardar. Usar un `value` interno que no pueda colisionar (`OTRA_PREPAGA` en `lib/perfil/opciones.ts` es el ejemplo real).
- **Un valor extraído por IA que va directo a una columna tipada** (`date`, `numeric`, etc.) siempre se valida/parsea antes del insert, nunca se manda tal cual — el schema de zod de la tool solo le pide el formato al modelo en la descripción, no lo garantiza. Si el insert falla por eso, se pierde toda la extracción (y un archivo ya subido queda huérfano) por un solo campo con formato raro. Ver `fechaValidaOnull` en `lib/estudios/nucleo.ts`.
- **Nunca asumir el `mediaType`/mime type real de un archivo subido por el usuario** — si no está en la lista de tipos que soporta la API (ej. HEIC de iPhone), declinar explícito en vez de mandarlo igual etiquetado como otra cosa (ver `TIPOS_SOPORTADOS` en `lib/estudios/extraer.ts`).
- **`lib/supabase/admin.ts` (`service_role`, bypassa RLS) es exclusivo de código de sistema que necesita leer datos de todos los usuarios a la vez** (hoy solo el detector de dosis vencidas) — nunca importarlo desde código que atiende una request de un usuario autenticado normal; para eso están `lib/supabase/{server,client}.ts`, que sí respetan RLS.
- **Dedupe "claim-before-send"**: cuando una acción externa (enviar un email, cobrar, etc.) no debe repetirse aunque el trigger corra más de una vez, el patrón de este repo es un `upsert(fila, {onConflict, ignoreDuplicates: true}).select().maybeSingle()` en una tabla con constraint único ANTES de ejecutar la acción — si no devuelve fila, alguien más ya la reclamó y no se hace nada. Ver `alertas_dosis` + `app/api/cron/dosis-vencidas/route.ts`. Comparar secretos de headers (`x-cron-secret`) siempre con `crypto.timingSafeEqual`, nunca `===`.
- **Un comentario JSDoc/de bloque nunca puede contener el literal `*/`** (ej. describir un cron `*/5 * * * *`) — cierra el comentario a mitad de frase y produce un error de sintaxis real (detectado en este pase corriendo `next dev` contra la ruta); hay que separar los caracteres (`` `*` `/` `5` ``) o parafrasear.
